The architecture the product needs

The core must not know Florence, CLIP, YOLO, Paddle, or any vendor. It knows capabilities; plugins provide implementations.

One core, three layers

CORE datasets · jobs · issues · labels · versions RUNTIME ONNX Runtime CPU CoreML · CUDA · DirectML · XNNPACK PLUGINS embedding · detection · OCR · face · segmentation any external plugin can join

Multimodal by contract

The contract should not say “use this model.” It should define inputs and outputs:

image → embedding [N] image + prompts → boxes / labels image → OCR regions / text image → face regions image + box / point → mask Every output carries: provider · model_id · revision runtime · checksum · confidence

Third-party plugins

A user can install a plugin for a capability not included in the catalog. The app discovers the plugin, shows its license and requirements, lets the user select a model, and keeps the same review flow.

plugin installed → capability registered model missing → “install” button model installed → “use” button provider unavailable → real reason, never fake results

What should not be a default

YOLO-World

Interesting because prompts can define custom classes, but it uses the Ultralytics ecosystem and the repository is AGPL-3.0. Do not bundle it without a legal decision.

do not preselect

Grounding DINO Tiny

Open-vocabulary and Apache 2.0, but approximately 0.2B parameters and a checkpoint around 689 MB. Excellent quality option; poor lightweight default.

too large

Cleanlab

It audits labels; it is not an installable model. The current job requires external pred_probs_path; first generate those probabilities reliably.

not a pack

Quality models

Download nothing. OpenCV/Pillow already cover the current detectors with deterministic, cheap, explainable behavior.

zero download

Technical decisions before code

Runtime

Use ONNX Runtime as the common path: CPU by default, with Execution Providers for CUDA, DirectML, CoreML, and XNNPACK.

CPU → always available Apple → CoreML when supported NVIDIA → CUDA when installed Windows → DirectML when available

Provider contract

The current registry only reports available(). A local provider must also run inference and declare capabilities.

model_id revision runtime license checksum preprocess_version output_schema

Safety rule

The model detects; a person decides. AI boxes enter as source_type=model, status=pending. PII becomes an issue. No score may silently quarantine an item.

Next steps

  1. Create a ModelSpec catalog with id, capability, license, runtime, size, checksum, and status.
  2. Add on-demand download with progress, cancellation, and checksum validation.
  3. Replace the fixed ViT-B-32 embedding with provider configuration; never mix indexes from different models.
  4. Implement Florence, OCR, and BlazeFace adapters; the current provider still contains hardcoded OpenAI logic.
  5. Measure all four packs on the local fixture before promising “fast.”
